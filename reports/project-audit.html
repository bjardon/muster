Keep the design. Tighten the execution rules.

Muster is appropriately small for a personal experiment. The sortie describes intent, provider adapters do the work, and the runtime controls integration and acceptance. SQLite and local Git worktrees are sensible choices. I found little outright over-engineering.

The main problem is that the runtime's state transitions span SQLite, Git, provider sessions, and child processes without enough recovery rules. A clean happy path works, but interrupted and overlapping operations can lose work or report the wrong outcome.

The most serious acceptance issue is independent of crashes. Command checks can modify the integration worktree, pass, and leave the accepted branch without the files they tested. Fix this before relying on an evidence-bearing PR.

What to preserve

Keep isolated worker worktrees, Cursor's sandbox and tool restrictions, Codex's sandbox, ordered routing, bounded attempts, and the draft-only PR rule.

Keep the trusted-host limitation explicit. This audit does not establish protection against malicious repositories or prove live SDK sandbox behavior.

Prioritized findings

High priority means the issue can undermine acceptance, lose unfinished work, or leave execution outside runtime control. Medium priority covers reproducibility, fallback, and bounded resource use. “Reproduced” means a local probe demonstrated the behavior; “code review” means the trigger follows from the implementation but was not exercised end to end.

11 findings
F01HighReproducedAcceptance

Checks can pass against files absent from the accepted branch

src/runtime.ts lines 127–146, 295–303 · src/git.ts lines 28–30

Command criteria execute directly in the integration worktree. The runtime records exit code zero as success, then pushes its Git branch and force-removes the worktree. It never checks whether the commands changed tracked files or created uncommitted source files.

Probe: a check created only-in-check.txt and verified that it existed. The run succeeded. git show muster/audit:only-in-check.txt failed because the accepted branch did not contain it.

Smallest reliable fix

Verify a specific commit in a disposable verification worktree. Reject tracked changes and non-ignored additions after checks. Permit ordinary ignored build output. Record the verified SHA and require that exact SHA before push.

Regression to add

A check that rewrites a source file or creates a required file must not produce acceptance. A check that only creates ignored build output should still pass.

F02HighReproducedRecovery / data loss

Resuming an interrupted assignment can delete its unfinished work

src/runtime.ts lines 224–250 · src/git.ts lines 23–30

An assignment persists its attempt number before creating its worktree. On resume, produceTask increments that number and tries to create a new branch at the same path. If the old worktree remains after a crash, creation fails and the catch block force-removes that path. With the default two attempts, a crash during attempt one can exhaust the task without invoking a resumed worker.

Probe: seeded the durable state of an interrupted first attempt and an uncommitted unfinished.txt. Resume exhausted attempt two and deleted the file.

Smallest reliable fix

Reconcile an existing assignment before allocating another attempt. Resume its owned worktree and compatible provider session. Preserve failed or cancelled worktrees until their changes are saved or deliberately discarded. Cleanup must not run merely because creation failed.

Regression to add

Terminate after worktree creation, during editing, and after commit creation. Resume must preserve edits and must not spend an extra attempt solely to discover an occupied path. Also test an agent that commits its own changes; commitChanges currently treats a clean index as no work.

F03HighReproducedIntegration recovery

Cherry-pick recovery uses a commit identity that does not survive integration

src/runtime.ts lines 149–165, 180–209 · src/git.ts lines 46–56

A worker commit cherry-picked onto a changed integration branch gets a different SHA. If the process dies between cherry-pick and status: completed, recovery tests whether the original worker SHA is an ancestor. It usually is not, so recovery cherry-picks the same change again and fails.

Probe: applied a worker commit after another integration commit. containsCommit returned false, and replay failed on an empty cherry-pick.

Smallest reliable fix

Give each integrated commit a durable assignment marker, and reconcile that marker before replay. Persist the resulting integration SHA. Handle an interrupted cherry-pick explicitly. A recorded result SHA alone cannot close the crash window before the database update.

Regression to add

Use two independent tasks from the same base. Interrupt after each cherry-pick and before each completion update. Resume should integrate every task exactly once. Reuse the same operation for repair tasks.

F04HighReproducedInput validation

Valid task IDs can collide with runtime-owned state and paths

src/types.ts lines 87–115 · src/git.ts lines 86–92 · src/runtime.ts lines 110–115, 149–152, 305–311

integration is a valid task ID and resolves to the integration worktree itself. repair-1 and verify-… can overlap runtime-generated task IDs in SQLite. Validation also accepts an empty acceptance contract and leaves dependency cycles to fail only after launch.

Two probes: a task named integration caused cleanup to delete the integration worktree; a sortie with no tasks and no criteria reported success. The repair/verifier ID overlaps are code-review findings.

Smallest reliable fix

Put workers under a distinct tasks/ directory and give stored assignments an explicit kind. As an immediate patch, reject reserved IDs and prefixes. Require a nonempty contract and validate field shapes, evidence kinds, and an acyclic graph before creating a run.

Regression to add

Cover reserved IDs, generated verifier collisions, self-dependencies, cycles, empty criteria, and malformed JavaScript exports. Keep an empty task list available only if verification-only sorties are intentional.

F05HighReproducedConcurrency

A failed task leaves sibling workers using a closed database

src/runtime.ts lines 73–90, 202–205, 246–250, 277–281

Promise.all rejects as soon as one assignment exhausts its attempts. The run handler marks the run failed and closes its store while sibling assignments remain active. Their subsequent events and state updates use that closed connection. With live workers, the process may still be doing provider work after status says failed.

Probe: one fake worker failed while another waited. executeRun returned before the slow worker finished; its later event raised a closed-database error.

Smallest reliable fix

Keep ownership of all dispatched promises until they settle. On fatal failure, choose an explicit drain or abort policy, then await all assignments before writing final status and closing the store. Keep any produced work recoverable.

Regression to add

A two-worker failure test should assert that no adapter is active and no callback occurs after finalization. Test cancellation at the same boundary. The current success fixtures all use concurrency one.

F06MediumCode reviewProvider fallback

A fallback provider receives the previous provider's session ID

src/runtime.ts lines 234–239, 265–280, 340–355 · src/store.ts task schema · cursor.ts lines 50–52 · codex.ts lines 14–16

The task stores one session_id, with no provider or model identity. The next route receives that value unchanged. If Cursor emits a session and then fails, a Codex fallback calls resumeThread with the Cursor ID. The reverse direction and verifier fallback have the same problem.

Smallest reliable fix

Store session identity with provider, model, and assignment attempt. Reuse it only when compatible. Keep an old session for evidence while starting a new provider session. Resolve the route list once rather than rereading it mid-run.

Regression to add

Have the first adapter emit a session then fail. Assert that the second provider starts fresh. Add a separate test proving same-provider resume retains its intended session and worktree.

F07HighReproducedProvider result

The Codex adapter returns success after a streamed failure

src/adapters/codex.ts lines 17–32 · installed @openai/codex-sdk/dist/index.d.ts lines 137–167

The stream handler observes messages and commands but ignores turn.failed and error. It returns normally when the stream ends, without requiring turn.completed. If a worker left partial edits, the runtime can commit them as a successful assignment. An empty verifier result fails closed during parsing, but it does not trigger the adapter fallback that a provider failure should.

Probe: replaced the SDK thread with a fake stream containing turn.failed. The real adapter resolved with an empty finalText. No Codex service was called.

Smallest reliable fix

Throw on SDK failure events, require successful terminal completion, and preserve diagnostic text. Give both production adapters the same success contract.

Regression to add

Test failure before output, failure after partial output, an abruptly ended stream, and normal completion. Also close Cursor's abort gap while Agent.create or agent.send is pending, and handle cancellation promise rejection.

F08MediumReproducedReproducibility

The approved run does not freeze its base commit or execution plan

src/cli.ts lines 63–87 · src/runtime.ts lines 43–46, 65–68, 94–97 · src/routing.ts lines 40–46

The run stores a branch name rather than its SHA. The runner resolves that name later. It also reloads the sortie and only hashes the contract, allowing task prompts, limits, and PR settings to change while keeping the same approval hash. Routing loads again at dispatch. These are reproducibility gaps even on a trusted host.

Probe: advanced main after creating the run record and before execution. The run included the later commit. Sortie and routing drift are established by code review.

Smallest reliable fix

Persist a base SHA separately from the PR base branch, plus the resolved sortie and route lists. Resume from those values. Keep the contract hash as the human acceptance reference.

Regression to add

Move the branch, edit the sortie, and change the routing file after launch. The queued or resumed run must retain its original plan, or reject the drift explicitly.

F09HighCode reviewRunner ownership

Resume can start a second runner before the first claims the run

src/cli.ts lines 118–125, 129–141, 169–182 · src/runtime.ts lines 64–71 · src/store.ts lines 109–115

Launch and resume spawn a detached child but do not atomically claim the run. The PID appears only after the child loads the sortie. Two resume commands can both see no live PID and launch competing runners. Both can operate on the same worktrees and overwrite state. A stored PID alone also cannot distinguish the original runner from a reused PID.

Smallest reliable fix

Use a transactional claim with an owner token and compare-and-set state changes. Only the owner may finalize. Handle child spawn errors and acknowledge startup before reporting it queued successfully. Reconcile cancellation when no runner remains.

Regression to add

Race two resumes while startup is delayed. Exactly one runner should enter the mission. Test spawn failure, stale ownership, and cancelling a paused run; today a paused cancellation can remain “cancelling” indefinitely.

F10MediumCode reviewResource bounds

A command can hang the run or fill memory with output

src/process.ts lines 9–32 · src/runtime.ts lines 298–303 · src/git.ts lines 63–82

The command helper concatenates all stdout and stderr in memory and has no deadline. The runtime then stores full check output in SQLite. A hanging test, Git credential prompt, or noisy command can keep a run alive indefinitely or exhaust memory. Git and PR operations do not receive the run's abort signal.

Smallest reliable fix

Add deadlines and cancellation to the shared process helper. Stream full output to a run log with a retention limit and retain a bounded tail for errors and evidence. Ensure descendant processes terminate, and record timeout or signal termination distinctly from a normal exit.

Regression to add

Exercise a hanging child, a child that spawns a descendant, a large-output command, and cancellation during push with a local fake executable. Assert bounded memory and no surviving children.

F11MediumCode reviewVerifier enforcement

Verifier mutation detection misses changes on failure and in already-dirty files

src/runtime.ts lines 339–355, 377–386

The runtime compares HEAD and git status --porcelain only after a successful adapter return. If an adapter writes and then throws, the next verifier can inspect contaminated state. A file that was already dirty can change content while its porcelain status stays identical. The sandbox remains the primary control; this check does not fully enforce the runtime's claimed invariant.

Smallest reliable fix

Start verification from a clean, known commit. Check content integrity in a finally path and reject mutation before fallback. Require a nonempty evidence string for an accepted JSON verdict; the current parser accepts {"accepted":true} with a placeholder.

Regression to add

Use a fake verifier that modifies then throws, one that edits an already-dirty file, and one that accepts without evidence. None should yield acceptance or silently contaminate a fallback verifier.

Recommended order

01 / Protect acceptance

Make “passed” mean the committed result passed

Address F01, F04, F07, and F11. These are bounded changes with deterministic tests. Reject invalid sorties before creating worktrees.

02 / Make recovery coherent

Give each assignment a recoverable lifecycle

Address F02, F03, F05, F06, and F09 together. Use typed records, transactional state changes, and one shared integration path. Avoid separate repair recovery rules.

03 / Prove the live path

Freeze inputs and bound execution

Address F08 and F10. Then complete the existing TODO's live Cursor implementation, Codex verification, and interrupted-run recovery exercises.

No rewrite is warranted. The existing provider seam earns its keep. Do not add an ORM, event-sourcing framework, plugin registry, distributed scheduler, or dashboard to solve these local lifecycle problems.

Small cleanup can accompany the fixes: remove unused byId in runtime.ts:176, centralize the Cursor model default, close CLI resources on error, remove the scripted delay's abort listener after completion, and restore routing environment variables and delete temporary directories in the existing tests.

What remains unproven

The review covered every source file, the existing tests, package/compiler configuration, README, TODO, and the installed Codex SDK event declarations. It was not a dependency vulnerability scan or a review of the private Notion devlog.

Runtime code and repository build status were left unchanged. This report and its evidence are audit artifacts, not shipped implementation work.
